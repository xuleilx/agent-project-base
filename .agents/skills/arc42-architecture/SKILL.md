# arc42 架构文档：代码与需求双模式

## 用途与边界

从代码描述现状架构，或从需求设计目标架构，输出中文 Markdown，遵循官方 arc42 十二章结构与写作指南，用 Mermaid 表达 C4 视图和动态视图。核心原则：**先分析、列证据、确认缺口与方案，再写正式文档；现状、需求、提案与已确认设计不混淆。**

适用于现有软件、脚本仓库、开发工具、模板项目及尚无代码的新系统；不预设它们是业务应用。允许提出并比较架构方案，但仅创建或更新架构文档，不实现功能、不修改应用源码或现有 OpenSpec 规格，不提交、推送或创建 PR。已有文档先读后改；遇到未知用户内容先确认。

本 skill 是按用户需求编写的项目自定义能力，不是 arc42 官方 skill，不引入第三方 arc42 toolkit，也不重写 Superpowers 开发流程。若当前任务是“创建此 skill”，只创建和验证 skill，不执行下面的架构文档生成任务。

## 模式选择

skill 名称为 `arc42-architecture`，以下 `code`、`requirements` 是输入模式标签，不是新增 CLI 命令或另一套 skill。

| 输入/用户目的 | 模式 | 描述对象与依据 |
| --- | --- | --- |
| 有代码，要求逆向或描述已实现系统 | `code` | 现状；源码、配置、可执行入口及实际验证记录 |
| 无代码，或明确要求按需求设计目标架构 | `requirements` | 目标；需求/PRD/用户陈述、约束、质量场景与设计决策，无源码也能开始 |
| 同时要求现状、目标及差异 | 双输入对照 | 分别执行两种模式的取证步骤，再做差异对照；不是把目标塞进现状 |

有代码不代表只能逆向：用户要求设计新能力时按目标处理。代码模式可读取需求解释目标，但不自动开展新方案设计。输入不足以判断用户要现状还是目标时，只问该边界；明确没有代码时不要求先交源码，也不把已明确需求全部降成 TODO。若用户仅给现状说明而无源码，记录“用户报告，实现未核实”，可以进行对照但不能冒充代码取证。

## 标准与证据规则

- 先读取目标项目已有架构资料与官方模板。此基座提供 `docs/arc42-template/arc42-template-ZH.md`；它不是所有目标项目都存在的前提。缺少时参考 [arc42 模板](https://arc42.org/download) 与 [写作指南](https://docs.arc42.org/)。无法访问时标注标准核对限制，不宣称完成官方认证。
- C4 语义以 [C4 Model](https://c4model.com/) 为准。引用或改编第三方模板内容时保留相应署名、来源和许可证；不复制带写作提示的空模板充当项目架构。
- 每条重要陈述记录 `来源类型 | 适用视角（现状/目标） | 状态`。代码事实采用 `已确认实现`、`推断`、`未验证假设`、`TODO`；需求采用 `已明确需求`、`待澄清需求`；方案采用 `提议`、`已确认设计`、`已拒绝/已替代`。用户提供的现状报告单列“用户报告，实现未核实”。已明确需求不是实现事实，已确认设计也不证明已经实现或测试通过。
- 每个重要陈述记录证据 ID。代码依据是已读的仓库相对路径、符号/配置键/文档标题；需求依据是需求文件与条款、已有需求 ID，或可定位的用户原话/确认记录。保留已有 ID，没有时分配 REQ-001 等稳定 ID；提案使用 DES-001 等 ID，并关联需求与权衡。没有代码时不编造源码路径、函数或行号；没有确认记录时设计仍是提议。只有亲自读取后才填写行号，跨章节复用 ID，源码链接用可解析的相对路径。
- 资料须标明项目/场景和版本范围；仅在同一目标且用户确认适用时复用需求或设计。独立项目/测试场景的指标、方案 ID、确认状态不能自动继承。每条目标度量都关联本范围的需求 ID；未提供的目标记 TODO，不从其他场景补入。
- 源码、配置说明的是声明行为；测试代码说明预期行为，实际测试输出才说明该次运行结果。设计文档说明意图，不等于当前实现。冲突并列记录，不能静默选一份作为事实。
- 验证记录使用四列：`命令 | 来源（本次执行/历史文档） | 实际输出或未运行 | 适用范围与限制`。没有本次执行输出时，当前验证状态就是“未运行”；README 中的历史通过数不能当本次结果。测试方法数从当前代码核对，与实际执行的测试数分开；分支/commit 同样要实际查询，无法查询就写未知，不能照抄历史资料。
- “未发现”必须带检索范围，不能升级为“不存在”。依赖锁定、目录存在、工具列表发现、宿主实际加载、运行成功分别取证。
- 不编造业务需求、性能实测值、已部署环境、已实现的故障恢复、历史决策原因或日期；用户给定指标是目标，不是测量结果。需求模式允许设计技术、部署和恢复方案，但必须关联需求/约束、注明提议/已确认设计及待验证内容；技术备选不能冒充用户规定。敏感配置只记录键名和脱敏含义。

## 六阶段工作流

建立六阶段任务列表并按顺序执行。先声明模式、现状/目标范围、资料版本与工具限制。代码资料记录 Git 基准（可获取时）、未提交变更和检索范围；需求资料记录文件版本、需求 ID 或用户原话来源。没有仓库/源码时记录“不适用”，不因此阻塞需求模式；不清理工作树。

### Phase 1：分析输入与边界

**代码模式**：先判断系统性质和边界，随后逐项追踪实际入口、调用、数据与依赖，而不是把目录名当运行模块。

| 必查领域 | 取证内容 |
| --- | --- |
| 项目目录 | 根目录、隐藏目录、软链接、生成物、vendored 代码；区分源码、资源、模板、测试及历史资料 |
| 构建系统与配置 | manifest、构建入口、脚本、工具链、版本约束、CI；安装管理与应用构建分开 |
| 源码与职责 | 可执行入口、关键类型/函数/脚本、调用关系、真实模块边界与依赖方向 |
| 第三方依赖 | 声明、锁文件、实际使用位置、版本、必要资源、许可证；生产/开发/测试/宿主依赖分开 |
| 公开 API 与接口 | 导出符号、HTTP 路由、CLI、配置格式、文件契约及版本/兼容性要求 |
| IPC 与通信 | 网络协议、消息队列、进程调用、文件交换、标准输入输出、共享内存；源/目标与方向 |
| 运行时与数据流 | 启动、成功场景、异常场景、状态读写、持久化、退出及资源释放 |
| 线程与并发 | 线程/进程、任务队列、异步调度、锁及共享状态；区分仓库实现与外部宿主行为 |
| 错误与日志 | 异常、返回码、重试/超时、错误传播、日志入口/输出/敏感信息处理 |
| 部署与启动 | 本地/容器/服务配置、环境变量、启动命令、外部前提；声明配置与实测环境分开 |
| 测试与配置 | 测试入口、覆盖范围、断言目标、夹具、配置差异和已运行/未运行验证 |

先列出覆盖隐藏目录与第三方资源的可执行文件清单（例如 Python、JavaScript、Shell 及无扩展名入口），对相关入口读取实现。只有检查了该范围的入口/实现后才写负面结论；仅阅读测试文件不能得出“仓库代码只有测试”“无 CLI/IPC/环境变量/并发/日志”。未读取的配套脚本单列为未分析范围，相应行为只能是 TODO，不能默认不存在。

某领域没有实现证据时，记录已检索文件/模式及“未发现”或“不适用”的理由。第三方配套脚本也纳入相关入口追踪；不能因主仓库没有业务服务就跳过并发、错误或通信检查。不得擅自启动服务、下载额外工具、安装依赖、访问生产环境或触发有副作用的测试；需要额外授权时说明缺口。

**需求模式**：从需求/PRD/用户陈述提取业务目的、干系人、用例、功能边界、硬约束、外部接口、数据生命周期、质量目标和验收场景。给每条需求保留/分配 ID，区分“用户明确要求”“技术尚未选定”“待澄清信息”。安全、通信、并发、错误/恢复、启动/部署、依赖、测试等未定义项列为设计议题，不因无实现全部写成不适用。需求已给 Linux/离线/单用户等条件时直接登记，不重复询问；量化目标补齐测量条件，不填虚构结果。

**双输入**：分别整理已核实代码事实、用户现状报告和目标需求；需求与当前实现冲突时记录差异，不把需求改写成已有能力。

### Phase 2：产出事实或需求清单

**先在对话中提交代码事实清单或需求清单，不生成十二章正文、正式图或 ADR。** 代码清单可用下列结构：

```markdown
## 分析范围
- 项目性质、资料根目录、基准、检索路径/模式、排除项、工具限制。

## 可执行入口清单
| 真实入口路径 | 所属资料根目录 | 是否读取实现 | 职责/未分析限制 |
| --- | --- | --- | --- |

## 架构事实
| ID | 领域 | 陈述 | 状态 | 证据路径与符号 | 限制/待确认 |
| --- | --- | --- | --- | --- | --- |

## 构建块与接口
| 构建块 ID | 实际职责 | 入口/接口 | 上下游 | 证据 ID |
| --- | --- | --- | --- | --- |

## 缺口与图适用性
- 缺失信息、矛盾、TODO；每种要求的图是否有证据支持及原因。
```

代码清单中每个必查领域都须有结论或显式缺口；IPC/通信、线程/并发、错误/日志须分别列行。采用已读取的真实路径和符号，不用占位事实填表。负面结论必须填写实际检索范围，表前列已读/未读的可执行入口，表后单列验证记录。只查一个 skill 子目录不能断言整个 `.agents/skills/` 无脚本；检索不到但范围尚未覆盖时标 TODO，不能将空清单当全仓库不存在的证明。需求清单不适用源码入口要求，使用下面的需求与设计议题字段。

需求清单使用固定字段：`需求 ID | 要求/约束 | 来源条款/用户原话 | 状态 | 质量场景/验收条件 | 缺口`。同时给出设计议题清单：`议题 ID | 关联需求 | 未定选择 | 待验证假设`，不将候选组件当事实。

双输入增加差异表：`差异 ID | 现状证据与核实状态 | 目标需求 ID | 目标设计 ID 与状态 | 差异/冲突 | 迁移与验证待办`。Phase 2 可先将目标设计列为未定；Phase 3 提案后补 ID。现状来源未核实时保留这一限制，不能用目标需求反证现状已核实。

### Phase 3：澄清缺口并确认方案

先给清单，再询问资料无法回答且会影响架构描述的信息，例如系统边界、业务目的、干系人、前三至五个质量目标、部署环境、未决接口和文档受众。问题关联事实/需求/缺口 ID，说明影响，避免重问项目或需求已回答的内容。

需求模式还须完成方案比较与确认：在已知需求和约束内给出通常两至三个可行技术/拆分备选；只有一个合理方案时说明依据。使用 `方案 ID | 关联需求/约束 | 容器/组件/接口/通信/数据/部署方案 | 利弊与质量影响 | 假设/风险 | 状态`，给出推荐但保持“提议”。说明并发、错误/日志、恢复与验证如何处理，不能仅列技术名。未知且会改变选择的问题先澄清；用户明确要先看备选时，可同时提供带假设的备选与待确认问题。

用户确认选定方案及假设后才标记“已确认设计”，再进入正式目标文档。确认采用文档方案不授权实现、迁移或部署。需求模式下允许设计未来组件、接口和 C4 视图，但这不证明它们存在；最终设计建立 `需求 → 设计/ADR → 构建块/接口/图 → 质量验收` 追踪关系。双输入同时说明迁移/兼容性、数据转换、回滚和验证计划，未知项 TODO，迁移未实施。

默认在此停下，等待用户回答或明确同意保留 TODO 后继续。没有实质缺口时，请用户确认范围及事实/需求清单；需求模式还须确认选定方案。**不以“资料够多”“仓库只是模板”或“赶时间”为由省略资料清单、缺口处理和应有的方案确认。**

如果用户明确更改确认约定（例如要求不提问），记录该变更；保留清单并将缺口列为 TODO，在其允许范围内继续，不能把省略确认变成补造信息或自动批准选型的授权。若要求直接出目标文档而未确认方案，可给明确标注“提议”的目标草案，不能写“已确认设计”。分析模式、只读模式或用户只要求执行到 Phase 3 时，在此返回，不写最终文档。

### Phase 4：生成十二章 arc42 文档

仅在允许继续后创建以下结构；每章写所选视角的内容、证据/需求依据、状态和未知项。根据官方模板覆盖子节，不用十二个空标题冒充完整文档。

代码模式写现状；需求模式写目标设计，并在各章注明提议/已确认设计、尚未实现及待验证项。双输入仍保留下面一套十二章文件，每章按适用性分为“现状”“目标”“差异与迁移待办”；某视角没有资料则写未知/不适用原因，不复制目标作为现状。代码事实与设计批准不能互相替代。

```text
docs/architecture/
├── README.md
├── 01-introduction-and-goals.md
├── 02-architecture-constraints.md
├── 03-context-and-scope.md
├── 04-solution-strategy.md
├── 05-building-block-view.md
├── 06-runtime-view.md
├── 07-deployment-view.md
├── 08-crosscutting-concepts.md
├── 09-architecture-decisions.md
├── 10-quality-requirements.md
├── 11-risks-and-technical-debt.md
├── 12-glossary.md
├── diagrams/
└── adr/
```

`README.md` 包含导航、输入模式与资料基准、现状/目标范围、事实/需求/设计索引、确认记录、假设与 TODO、图适用性及验证报告，承接 Phase 2/3 的结果，便于 Git 维护。需求模式增加需求追踪矩阵，双输入增加差异表；不为无代码虚构 Git 基准。无图或 ADR 适用时不造文件来填目录；空目录不会被 Git 跟踪，在 README 记录省略原因。

| 章 | 必写内容 |
| --- | --- |
| 1 Introduction and Goals | 需求概览、业务目的、质量目标与干系人；缺失业务信息用 TODO |
| 2 Architecture Constraints | 技术、组织、权限和标准约束；区分用户约定、工具限制与实施事实 |
| 3 Context and Scope | 业务上下文、技术上下文、系统边界、外部参与者/系统及接口 |
| 4 Solution Strategy | 代码模式解释现有策略；需求模式记录方案比较、选定策略及其如何支持需求/质量目标，引用带状态的决策 |
| 5 Building Block View | 现状构建块的实际职责/接口与来源；或目标构建块的设计职责/接口/依赖与需求追踪；按需 C4 L2/L3 |
| 6 Runtime View | 现有调用链或设计的成功/错误/退出场景；参与者、数据与状态变化，区分观察行为和预期行为 |
| 7 Deployment View | 已知环境/启动配置，或关联约束的计划部署/启动前提；未部署、未运行明确标注，不虚构成功命令 |
| 8 Crosscutting Concepts | 已有横切实现或目标并发、通信、配置、持久化、安全、错误/日志、恢复和测试设计；各自注明依据和状态 |
| 9 Architecture Decisions | 历史/现有决策与新设计提案/已确认设计分开；重要决策关联 adr/，记录确认依据 |
| 10 Quality Requirements | 质量树或分组、质量场景（刺激源、刺激、环境、对象、响应、度量）；需求指标标为目标，附验收计划，实测结果单列 |
| 11 Risks and Technical Debt | 现有风险/债务或目标设计风险的依据、影响、优先级；计划措施与已实施措施分开，未实现方案不冒充已有技术债 |
| 12 Glossary | 文中使用的业务和技术术语、缩写、同义词；避免与源码符号含义冲突 |

ADR 记录可追踪的历史决策或本次目标设计：ID、标题、状态、上下文、关联需求、决定/提案、备选、后果和证据/确认记录。逆向时不知道历史备选或权衡就标记未记录，源码选择不能伪装成当时理由。正向时记录本次实际比较的备选和权衡；未确认标“提议”，确认后标“已确认设计”，不得写成“已实现”。需求变化导致设计过期时标记“待重新确认/已替代”，不要覆盖历史确认。

### 图规则：C4 语义与 Mermaid 表达

每张图注明现状/目标视角、视图类型、边界、节点/边的证据或需求/设计 ID、状态和限制。现状图依据代码或明确标注未核实的现状报告；目标图依据需求、约束及带状态的设计推导，未批准标“提议”，已确认也必须标“目标设计，未实现/未验证”。需求不唯一决定技术方案，因此给出推导与权衡，不能声称组件由需求直接证明存在。用稳定逻辑构建块 ID 跨视图关联；双输入的图源命名为 `asis-*.mmd`、`target-*.mmd`，不覆盖同名现状图。

- **System Context Diagram（C4 L1）**：所描述系统、真实或需求明确的参与者、直接相连外部系统与关系；拟引入外部系统须关联设计并标目标。
- **Container Diagram（C4 L2）**：现状应用/数据存储，或目标设计的应用/数据存储，注明职责、技术与通信。Container 不等于 Docker 容器或任意目录；文件目录只有在存储职责与读写关系有现状证据/目标设计依据时才表示数据存储，不能伪装成服务。
- **Component Diagram（C4 L3）**：在一个已识别容器内细化有职责和接口的组件；不能从目录树自动推导组件。
- **Runtime Sequence Diagrams**：使用 `sequenceDiagram`，现状按入口/调用链取证，目标按用例与设计接口描述预期交互；未知宿主行为单独标注，预期响应不是实测行为。
- **Deployment Diagram**：使用 Mermaid C4Deployment 或带部署节点边界的 `flowchart`，表示已知环境/实例，或满足需求约束的计划环境/实例。目标端口/节点/服务是设计选择，标记状态与依据，不伪装成已部署。没有生产部署不等于视图不适用，本地运行前提与宿主映射也可描述。
- **State Machine Diagrams**：实际状态字段/事件/转换有证据，或目标状态/事件/转换有需求和设计依据时使用 `stateDiagram-v2`，注明视角与状态；开发阶段列表不自动等于运行状态机。

优先使用宿主支持的 Mermaid C4 语法。若渲染器不支持，使用标明 C4 层次/边界/类型的 `flowchart` 并记录限制；C4Context/Container/Component 不混用。代码模式下，仓库只是静态模板且没有可确认的应用/存储边界时，容器/组件/运行状态图可“不适用”，用标注为静态资产依赖的图说明真实关系；不以此否定需求模式的目标设计视图。

代码模式仅生成现状证据支持的图；需求模式可生成关联需求与明确设计方案的目标 C4/时序/部署/状态图，无源码不是禁画理由，但不得虚构已实现的系统。缺少依据的要求图在 README 解释缺口或不适用原因，不用想象业务凑数量。图源保存在 `diagrams/*.mmd`，对应章节以 Mermaid 代码块展示相同内容并检查一致性。支持的渲染工具存在时执行语法验证；没有时明确“未执行渲染验证”，不能把阅读代码等同渲染通过。

### Phase 5：架构一致性检查

逐项检查并记录实际结果；问题只修正文档，不通过修改应用源码消除矛盾。

- 十二章、导航、相对路径与 ADR/源码引用完整有效；必查领域均有事实或理由充分的缺口。
- 代码陈述的路径/符号真实存在，需求陈述可定位到条款或原话，设计可回溯需求与确认/提案；计划组件/符号不得要求其已存在，也不能为通过检查创建源码。图的节点/关系/方向有对应视角的依据，状态不跨章升级。
- 系统边界、构建块 ID、接口名称、依赖方向、数据存储、配置、版本在各章与所有图中一致。
- 运行时参与者来自同一视角的上下文/构建块；现状部署映射真实容器，目标部署映射目标容器并注明未部署；静态资产不是未经证明的服务。
- 第 1/10 章质量目标一致，第 4/9 章策略与决策一致，第 11 章不将建议措施当已实现能力。
- TODO/推断/未验证假设保留状态，需求/设计确认不升级为实现或测试；目标指标与测量结果分列，图源与章节一致。
- 需求模式检查需求覆盖矩阵、硬约束冲突、方案确认记录、质量场景/验收计划；未知容量、恢复条件和可行性保留缺口，不声称性能已证明。双输入逐条检查现状→目标差异、迁移/兼容/回滚与验证待办，目标不得出现在现状链路中。
- 如有适用且获授权的现有 Markdown/Mermaid/测试工具，执行并记录命令、输出及范围。无工具只做可执行的引用/结构与人工语义检查，列出跳过项。结构 lint 通过不等于架构正确。

### Phase 6：给出审查报告

在 README 的“审查报告”及最终回复中汇总：输入模式、产出文件、资料基准与现状/目标范围、事实/需求/设计覆盖、十二章完整性、方案确认状态、差异与迁移待办、已修复矛盾、遗留风险/TODO、验证命令与实际输出、未运行验证及原因。结论区分“检查通过”“有保留通过”“阻塞”；明确设计一致性不是实现正确性或性能证明，不使用未经核实的“全部验证完成”。

这是一份文档一致性与证据审查，不宣称代码审查、运行时证明或官方认证。用户另行要求代码审查时使用相应审查机制，不擅自扩展修改范围。

## 常见误区与停止信号

| 误区/信号 | 正确处理 |
| --- | --- |
| “设计文档很完整，直接写最终版” | 先对照当前入口/源码取证，提交事实清单并处理缺口 |
| “目录就是模块，锁文件就是容器” | 识别真实职责与接口；静态资产/数据存储/运行单元分开 |
| “文档说可用，所以所有 IDE 加载都成功” | 文档意图、发现结果和实测加载分别记录 |
| “没有业务服务，所以无需查线程和日志” | 追踪相关脚本与外部宿主边界，记录检索范围 |
| “十二章和所有图都必须填满” | 每章有真实内容或 TODO；不支持的图写原因，不虚构 |
| “格式检查过了，所以架构和性能已验证” | 报告工具能力边界、实际输出及未验证项 |
| “README 写过 4/4，所以本次测试通过” | 历史记录单列；本次没有命令输出即未运行，当前数量核对代码 |
| “只读过测试，但能断言整个仓库无脚本/通信/日志” | 补入口清单与实现读取，或缩小结论范围并标注未分析项 |
| “没有代码，所以不能分析需求或画目标图” | 需求模式从需求与设计取证，不要求虚构源码 |
| “500ms 写进需求，所以测量已达标” | 已明确需求的目标与本次/历史测试结果分列 |
| “用户想迁移 SQLite，所以已批准选型并迁移完毕” | 保留需求、提议、已确认设计、已实现之间的边界 |
| “代码和需求一起给，合并一套事实就行” | 每章按现状/目标/差异拆开，未经核实的现状报告保留限制 |

发现上述信号、失效引用或未经标记的推断时，暂停当前生成步骤，回到相应事实/需求/设计核对；新增重大缺口交给用户确认。

## 调用示例

- 代码模式：“使用 arc42-architecture，按当前代码生成现状架构，先到 Phase 3 给事实清单。”
- 需求模式：“使用 arc42-architecture，按以下需求生成目标架构。我还没有代码，先列需求、缺口和备选方案，等我确认。”
- 双输入：“代码是现状，PRD 是目标；分别标出现状、目标和差异，不把目标组件写成已实现。”
